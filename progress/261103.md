# 261103 — Cube Stack 최소 재현 (CaP-X)

## 목적
- CaP-X(Code-as-Policy) 셋업이 이 머신에서 유효한지 보이기 위해 Robosuite **Cube Stack** 결과를 작은 규모로 재현한다.
- 논문 Figure 8의 일부(**skill library ablation**)를 toy 규모로 재현해서, 사람이 만든 고수준 API 없이 저수준 API + 자동 생성 skill library로 어디까지 가는지 확인한다.
- 이후 safety/alignment 취약점 연구(e4)의 기준선으로 쓴다.

## 환경
- 커밋: `53e9966` (cap-x main)
- 머신: TITAN RTX 24GB (PyTorch로 쓸 수 있는 유일한 GPU), RAM 15GB, 20 CPU
- 환경: `.venv` — robosuite 1.5.1, mujoco 3.5.0, torch 2.9.1+cu128
- LLM: `google/gemini-3.1-pro-preview` (OpenRouter 프록시 `:8110`)
- 서버: PyRoKi `:8116` (IK), SAM3 `:8114` (분할), GraspNet `:8115` (grasp)
  - SAM3, GraspNet은 `CUDA_DEVICE_ORDER=PCI_BUS_ID CUDA_VISIBLE_DEVICES=2`로 TITAN RTX에 올림.
  - Molmo 서버는 쓰지 않음.
- ID 규칙: `eN` = 큰 태스크(브랜치 하나 단위), `eN-M` = 그 안의 작업

| e1-2 | Gemini single-turn, privileged | `cube_stack/franka_robosuite_cube_stack_privileged.yaml` | 23/25 | 92% | [75.0, 97.8]% | $0.84 |
| e1-3 | Gemini multi-turn VDM (SAM3 인식) | `cube_stack/franka_robosuite_cube_stack_multiturn_vdm.yaml` | 14/20 | 70% | [48.1, 85.5]% | $5.18 |

- 95% CI는 Wilson 구간.
- e1-1: 시뮬레이터, 로봇 API, 성공 판정이 정상 → LLM 결과가 낮으면 셋업이 아니라 모델 쪽 문제.
- e1-2: 모든 trial이 첫 코드 한 번으로 끝남(재생성 0). 실패 2건은 코드는 실행됐지만 적재 실패.
- e1-3: repo 회귀 테스트 기준(~79%)이 CI 안에 들어감 → 재현됨. 평균 코드 블록 3.5.
- privileged는 시뮬레이터의 정확한 물체 위치를 받고, VDM은 카메라 영상에서 SAM3로 직접 찾음 → VDM이 더 어려운 설정.

## e5 — Skill library ablation (Figure 8 일부)

모두 multi-turn VDM, Cube Stack, Gemini 3.1 Pro. 차이는 LLM에게 주는 API뿐이다.

| 설정 | API | 성공 | 성공률 | 95% CI | 평균 turn | 비용 |
|------|-----|------|--------|--------|-----------|------|
| 참고: 고수준 API (e1-3) | `FrankaControlApi` | 14/20 | 70% | [48.1, 85.5]% | 3.5 | $5.18 |
| ① 저수준 API | `FrankaControlApiReduced` | 7/10 | 70% | [39.7, 89.2]% | ~3.0 | ~$2.9 |
| ② 저수준 + skill library | `FrankaControlApiReducedSkillLibrary` | 10/10 | 100% | [72.2, 100]% | ~1.4 | ~$6.0 |

- config: ① `cube_stack/franka_robosuite_cube_stack_multiturn_vdm_reduced_api.yaml`, ② `..._reduced_api_skill_lib.yaml` (API 클래스 한 줄만 다름).
- API 차이:
  - 고수준: `get_object_pose`, `sample_grasp_pose`, `goto_pose` — 인식·좌표 변환·grasp를 API가 처리.
  - 저수준: `get_observation`, `segment_sam3_text_prompt`, `plan_grasp`, `solve_ik`, `move_to_joints` — 역투영, 좌표 변환, grasp 선택을 LLM이 직접 코드로 작성.
  - skill library: 저수준 + `mask_to_world_points`, `select_top_down_grasp` 등 유틸 9개 (이전 실행에서 자동 합성된 함수).
- 해석:
  - skill library를 붙이면 성공률 70% → 100%, 평균 turn이 절반 이하로 줄고 대부분 첫 코드에서 성공.
  - 저수준 + skill library가 사람이 만든 고수준 API(70%)보다 높음 → 논문 주장과 같은 방향.
  - n=10이라 ①과 ②의 CI가 겹침 → 통계적으로 확정된 차이는 아님.
- 조건: Molmo 서버 없이 실행. LLM이 `point_prompt_molmo`를 부르면 실패하고 SAM3로 대체함(①, ② 동일 조건).

## 실행 방법
```
# 서버
uv run --no-sync --active capx/serving/launch_servers.py --profile minimal        # PyRoKi :8116
uv run --no-sync --active capx/serving/openrouter_server.py --key-file .openrouterkey --port 8110
CUDA_DEVICE_ORDER=PCI_BUS_ID CUDA_VISIBLE_DEVICES=2 python -m capx.serving.launch_sam3_server --port 8114 --device cuda --host 127.0.0.1
CUDA_DEVICE_ORDER=PCI_BUS_ID CUDA_VISIBLE_DEVICES=2 python -m capx.serving.launch_contact_graspnet_server --port 8115 --device cuda --host 127.0.0.1

# 실험 (config만 바꿔서 실행; RAM 15GB라 VDM 계열은 worker 2개)
MUJOCO_GL=egl uv run --no-sync --active capx/envs/launch.py \
  --config-path env_configs/cube_stack/<config>.yaml \
  --model google/gemini-3.1-pro-preview --total-trials N --num-workers 2 \
  --output-dir outputs/repro/<name>
```
